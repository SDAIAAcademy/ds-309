When k-anonymity is not enough

k protects the fields you chose against the attacks you imagined

Homogeneity

Everyone in the class shares the sensitive value.

Background knowledge

The attacker knows a field you did not treat as a quasi-identifier.

Repeated releases

Two treated versions of the same table, intersected, shrink the classes.

Takeaway. Treat row-level releases as personal data under an agreement, even at k of five. For published numbers, use a control with a guarantee: Session 2.

The guideline asks the controller to evaluate the effectiveness of anonymisation techniques and keep them up to date; these three limits are why. The repeated-release attack is the bridge to differential privacy, whose budget accounts for repetition by design.

Differential privacy

The output barely depends on whether any one person is in the data

  • Two datasets that differ by one applicant
  • A randomised release gives almost the same distribution of outputs on both
  • Epsilon bounds "almost": smaller epsilon, closer distributions, more privacy
  • It holds whatever the attacker knows, including every other record

What it does not promise

That nothing about the population is learnt. A count shows that a district has many approvals; that is the point of publishing it.

Keep the formal definition in the notes: for neighbouring datasets D and D' and any set of outputs S, the probability of S under D is at most e to the epsilon times its probability under D'. The guarantee is about the individual's contribution, not about secrets of a group. Sources: Dwork and Roth, The Algorithmic Foundations of Differential Privacy.

For integer counts the library uses the discrete version of the Laplace distribution, so released counts stay whole numbers. The whole vector of 59 counts has sensitivity 1, not 59, because each applicant is in exactly one district. That point returns in Session 3 as parallel composition.

Lab 2.2 in five lines

The library builds the measurement and tells you what it spends

import opendp.prelude as dp
dp.enable_features("contrib")
domain = dp.vector_domain(dp.atom_domain(T=int), size=59)
meas = dp.m.make_laplace(domain, dp.l1_distance(T=int), scale=1 / eps)
released = meas(counts)          # 59 noisy counts
meas.map(d_in=1)                 # the epsilon spent when one person changes
Check the claim with the library. map computes the privacy loss from the domain, the distance and the scale. Never trust an epsilon typed in a report.

From a curve to a decision

Choose the smallest budget that meets the accuracy the use needs

  • The use: a dashboard that compares districts
  • The rule agreed with Bashayer: typical error under 5% in the smallest districts
  • 0.1 fails (16%), 0.5 meets it (3.1%), 1.0 meets it with margin
  • Recommendation: epsilon 0.5 per release

The budget is per release

A monthly refresh at 0.5 spends 6 a year. Session 3 is about that.

The accuracy rule comes from the use, not from privacy. Write it down before looking at the errors, otherwise the budget is chosen to fit the result. The LO3 evidence is the error-against-budget plot that Lab 2.2 saves and this recommendation with its reason.

After the noise

Anything computed from a released value spends no more budget

Clamp

Negative counts set to zero.

Round

Whole numbers for a dashboard.

Aggregate

Regional totals summed from district counts.

What goes wrong. Recomputing from the true data "to fix" a strange noisy value is not post-processing. It spends budget, usually without anyone noticing.

Post-processing immunity is why a released noisy table can be published, charted and summed freely. The failure in the callout is common: someone sees a small district at 0 and "corrects" it from the source table, leaking exactly what the noise hid.

Spending a budget

Epsilons add up over the same people, not over different people

Sequential composition

Two releases about the same applicants: the epsilons add. Mean income at 0.3 and household size at 0.2 spend 0.5.

Parallel composition

Releases about disjoint people: the largest epsilon counts once. 13 region counts at 0.1 spend 0.1, not 1.3.

The two rules are the whole of budget accounting in this course. Ask the room: the dashboard of Session 2, refreshed monthly at 0.5. Same people each month, so sequential: 6 a year. Advanced composition theorems give tighter totals; mention them by name only.

A different kind of release

A synthetic extract keeps the patterns and replaces the people

  • Fit a model of the table, then sample new rows from it
  • Useful where the analyst needs rows: a hackathon, teaching, testing a pipeline
  • No row is a real person, if the model did not memorise them
  • That "if" is tested, every time, before release

No guarantee by default

An ordinary generator gives no formal privacy guarantee. A generator trained with differential privacy does, at a cost in utility.

The capability slot is "synthetic tabular data", with the Synthetic Data Vault and synthpop as examples. The lab writes the sequential method in scikit-learn so that participants see why it can copy records. SDV 2.2 and synthpop 1.9 were the current releases when the course was built. Sources: Synthetic Data Vault documentation; synthpop on CRAN.

How the lab's generator works

Each column is drawn from a tree fitted on the columns before it

1 · agedrawn from observed ages
→
2 · gendertree on age
→
3 · ...tree on all earlier columns
→
4 · decisionvalue taken from a training row in the same leaf
What goes wrong. If a leaf may hold a single training row, the "donor" is always that row: the synthetic row becomes a copy of a real person.

This is the classification-and-regression-tree method that synthpop uses by default, written in about fifteen lines. The minimum leaf size is the knob that trades fidelity for privacy. Sources: Nowok, Raab and Dibben, synthpop: Bespoke Creation of Synthetic Data in R (2016).

Is the file useful?

Measure utility on the shares and on a model trained on synthetic rows

Marginal distance

Total variation distance between real and synthetic shares of each categorical column, averaged. 0 is identical.

Train synthetic, test real

A model predicting the officer's decision, trained on synthetic rows and scored on real rows it never saw. Compare with the same model trained on real rows: AUC 0.936.

The real-trained AUC 0.936 is from the reference run of Lab 2.4 on 8,000 training rows. Marginals check that the shares survive; the model checks that relationships survive, which is what an analyst uses.

Does the file leak?

Compare distances to the training rows with distances to unseen rows

Exact copies

Synthetic rows identical to a training row, against the same share for holdout rows.

Distance to closest record

Share of synthetic rows closer to the training set than to the holdout. 50% means no preference.

Membership inference

Score each real record by its nearest synthetic row. AUC 0.5 means the attacker cannot tell members.

The holdout is the control group: coarse data repeats naturally, so the question is never "are there copies?" but "are there more copies of training rows than of rows the generator never saw?". The membership attack used here is the simplest one; stronger attacks exist, so a pass is evidence, not proof.

The recommendation

Release the leaf = 200 file for the hackathon, under stated limits

  • Passes: copies near baseline, membership AUC 0.511, utility within 0.003 AUC

A recommendation names what passed, what it is for, and what it is not for. Small groups are poorly reproduced by any generator with large leaves: the stretch plants a rare combination to show it.
